# Environment Strategy

How configuration differs across **local**, **staging**, and **production**, and the contract every environment must satisfy.

The shape of the platform is the same everywhere. Only URLs, secrets, and certificates change. If you find yourself writing per-environment code (a `switch ENV` in a service), that's a bug in this strategy.

---

## 1. The contract every environment must satisfy

| Property | Why |
|---|---|
| Keycloak is reachable via HTTPS at a stable hostname | OIDC iss claim must match across token issuance and validation |
| `KC_HOSTNAME` set to the public canonical URL | Issuer in tokens + discovery doc stays stable regardless of network path |
| `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` | Internal services can reach Keycloak by an internal name without breaking discovery's `issuer` claim |
| `KC_PROXY_HEADERS=xforwarded` | Keycloak trusts upstream TLS termination so redirect URLs are correct |
| APISIX fetches OIDC discovery from an internal URL | Avoids needing the TLS CA inside the gateway container |
| All service-to-service auth uses bearer JWTs validated by APISIX | One auth surface; defence-in-depth via service-side scope check |
| No public-key material in version control | Keys are fetched live or stored in a secret store |

If an environment can't satisfy one of these, the platform should refuse to come up rather than degrade silently.

## 2. Per-environment configuration matrix

| Concern | local | staging | production |
|---|---|---|---|
| Public auth hostname | `auth.guva.localhost` | `auth.staging.guva.go.ug` | `auth.guva.go.ug` |
| Public API hostname | `localhost:8000` *(to be migrated to `api.guva.localhost` in a follow-up)* | `api.staging.guva.go.ug` | `api.guva.go.ug` |
| TLS termination | Caddy with internal CA | Caddy or cloud LB with ACME (Let's Encrypt staging) | Cloud LB with ACME (Let's Encrypt prod) + WAF |
| Keycloak realm DB | Local Postgres | Managed Postgres, single-AZ | Managed Postgres, multi-AZ + PITR |
| Keycloak deployment | Single container, `start-dev` | StatefulSet, `start` (production mode) | StatefulSet, `start` (production mode), HA across AZs |
| Realm export source | `deploy/compose/keycloak/realm-export.json` (committed sample) | Realm export checked into infra repo (scrubbed of secrets) | Same; production realm is its own export |
| Client credentials | Inline in realm export *(dev-only secret)* | Sourced from Vault at Keycloak boot via custom init script | Same as staging; Vault-backed HSM-anchored secrets |
| APISIX deployment | Single standalone container | Multiple replicas behind a load balancer, etcd-backed config | Same as staging; HA across AZs; etcd cluster |
| APISIX discovery URL | `http://keycloak:8080/realms/guva/.well-known/openid-configuration` | `http://keycloak.guva.svc.cluster.local:8080/...` | Same as staging |
| Reference service (and other backends) | `go run` on host | Kubernetes Deployment | Kubernetes Deployment, HPA |
| Observability target | local Prometheus + Grafana | Central Prometheus + Grafana (cluster-scoped) | Same; longer retention; alerting wired to PagerDuty |

The shape is identical. Hostnames, replica counts, and secret storage change.

## 3. Secret strategy

> **Never commit a secret. Public keys, hashes of secrets, and example dev-only credentials are acceptable; anything that grants access to a non-dev resource is not.**

| Secret | local | staging | production |
|---|---|---|---|
| Keycloak admin password | `admin/admin` in compose env | Vault `secret/keycloak/admin-password` | Same; rotated quarterly |
| Realm signing key | Auto-generated by Keycloak, persisted in volume | Same | Same; rotation drilled semi-annually (see [RUNBOOK-AUTH.md §3](./RUNBOOK-AUTH.md)) |
| `guva-reference` client secret | Inline in realm export | Generated at provisioning, stored in Vault, injected via init script | Same |
| Postgres passwords | Compose env | Vault | Vault, HSM-anchored |
| TLS certs / keys | Caddy's auto-generated CA | ACME (Let's Encrypt staging) | ACME (Let's Encrypt prod) + cert-manager |
| OTel collector exporter creds (if any) | None | Vault | Vault |
| Webhook signing secrets | Returned to consumer at registration; hash stored in DB | Same | Same |

The repository contains zero real secrets. Anything that looks like one (e.g., `reference-dev-secret` in the realm export) is a local-only value.

## 4. Migrating an existing local-dev consumer to staging

A worked example: take the `guva-reference` integration from local and run it against staging.

1. **Provision the client in the staging realm.** In Keycloak's admin console (or via the realm export in the infra repo), create a `guva-reference` client with the same scopes (`verify:citizen`, `audit:read`). Generate a fresh client secret; store it in Vault at `secret/services/reference/staging/client-secret`.

2. **Point the service at staging.** Set environment variables on the consumer:
   - `KEYCLOAK_URL=https://auth.staging.guva.go.ug`
   - `CLIENT_ID=guva-reference`
   - `CLIENT_SECRET` ← resolved from Vault at process boot
3. **Confirm trust.** The staging cert is from Let's Encrypt — already trusted by every modern OS. Run a `curl https://auth.staging.guva.go.ug/realms/guva | jq .public_key` to confirm.

4. **Run a smoke test.**
   ```bash
   TOKEN=$(curl -sS -X POST https://auth.staging.guva.go.ug/realms/guva/protocol/openid-connect/token \
     -H 'Content-Type: application/x-www-form-urlencoded' \
     -d 'grant_type=client_credentials' \
     -d "client_id=guva-reference" \
     -d "client_secret=$CLIENT_SECRET" | jq -r .access_token)
   curl -sH "Authorization: Bearer $TOKEN" https://api.staging.guva.go.ug/v1/reference/ping | jq
   ```

5. **What can go wrong, and the fix.**

   | Failure | Likely cause | Resolution |
   |---|---|---|
   | `401 invalid_token: jwt signature verification failed` | Wrong realm or fresh tokens fetched before APISIX refreshed JWKS cache | Wait ~30s for cache refresh, or restart APISIX |
   | `401 invalid_token: iss returned failure` | `KC_HOSTNAME` in the env doesn't match the hostname clients fetch tokens via | Audit env vars on the Keycloak deployment |
   | `403 insufficient_scope` | Client wasn't granted the route's required scope | Add to default-client-scopes in the realm |
   | `Network is unreachable` from inside APISIX during discovery | APISIX can't reach the internal Keycloak service | Check NetworkPolicy / Service / DNS in the cluster |

## 5. Promotion checklist

Before promoting a change from local → staging → production, every change should satisfy:

- [ ] Auth-related: token validation works for `guva-reference` on the target environment
- [ ] No secret values added to any committed file (run `pre-commit run gitleaks --all-files`)
- [ ] Any new realm role / scope is present in the target realm
- [ ] Any new APISIX route declares its required scope
- [ ] Health endpoints (`/healthz`, `/readyz`) return 200 on the deployed service
- [ ] OpenAPI spec under `services/<name>/api/openapi.yaml` matches the deployed routes (contract tests green)
- [ ] Observability: `up{service="<name>"}` shows in Prometheus
- [ ] Rollback path documented (see [ROLLBACK-PHASE-2.md](./ROLLBACK-PHASE-2.md) for the auth migration template)
